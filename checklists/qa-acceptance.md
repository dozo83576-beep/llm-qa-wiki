# Приёмка и сдача заказа

Финальный гейт перед передачей результата заказчику. Срабатывает после закрытия фазы `qa-report` и до
отправки файла.

Формат: **критерий** — проверка — owner — severity.

## Полнота работ

- [ ] **Каждый критерий из тест-плана имеет статус** — QA — block — [Тест-план](../docs/04-documentation/test-plan.md).
- [ ] **Все запланированные кейсы выполнены** либо помечены `Blocked` с причиной — QA — block.
- [ ] **Ключевые пользовательские сценарии пройдены end-to-end** — QA — block.
- [ ] **Непокрытые области перечислены явно** с причиной — QA — block — [Оракул и границы](../docs/01-fundamentals/test-oracle-and-limits.md).
- [ ] **Проверено на всех средах из матрицы** — QA — block.

## Качество отчёта

- [ ] **Валидатор отчёта проходит без нарушений** — QA — block — [Спецификация](../docs/14-templates/xlsx-test-management.md).
- [ ] **Нумерация кейсов сплошная**, прогон покрывает все кейсы — QA — block.
- [ ] **Каждый Fail связан с существующим дефектом**, у Pass поле пустое — QA — block.
- [ ] **Перелинковка на месте**: `Case ID` и `Bug ID` на `Test Run`, `Related Case ID` и
      `Session ID` на `Bug Reports` ведут на свою строку — QA — block.
- [ ] **Поле `Tester` заполнено именем** того, кто вёл заказ — QA — block.
- [ ] **Числа в сопроводительном сообщении сходятся с файлом** — QA — block — [Отчёт](../docs/04-documentation/test-summary-report.md).
- [ ] **Ожидаемые результаты измеримы**, без формулировок «работает корректно» — QA — warn.
- [ ] **Каждый основной PNG показывает результат своего кейса**; переходы имеют «до/после» или
      запись, невидимые свойства — измерение, точных дубликатов основных PNG нет — QA — block —
      [Доказательства](../docs/09-automation/evidence-collection.md).

## Качество дефектов

- [ ] **Каждый дефект воспроизведён автором** по собственным шагам — QA — block — [Воспроизводимость](../docs/05-defect-management/reproducibility.md).
- [ ] **У каждого дефекта указано окружение** — QA — block.
- [ ] **Доказательства приложены ссылками** и открываются — QA — block — [Доказательства](../docs/09-automation/evidence-collection.md).
- [ ] **Severity обоснована** по таксономии — QA — warn — [Severity](../docs/05-defect-management/severity-vs-priority.md).
- [ ] **Дефекты Critical сообщены заказчику отдельно**, не только в отчёте — QA — block.
- [ ] **Рекомендации отделены от дефектов** — QA — warn.

## Приватность

- [ ] **В отчёте и доказательствах нет персональных данных** — QA — block — [Персональные данные](../docs/11-security-accessibility/personal-data.md).
- [ ] **Нет учётных данных, токенов, паролей** ни в тексте, ни на изображениях — QA — block.
- [ ] **Ссылки на доказательства не имеют срока истечения** — QA — warn.

## Завершение

- [ ] **Созданные тестовые объекты удалены** или переданы списком — QA — warn — [Тестовые данные](../docs/12-process-and-metrics/test-data.md).
- [ ] **Оценка готовности сформулирована через критерии выхода**, а не как решение о релизе — QA — block — [Роль тестировщика](../docs/01-fundamentals/tester-role.md).
- [ ] **Граница «дефект против новой задачи» проговорена** — QA — warn.
- [ ] **Опыт зафиксирован** в вики либо записано, что фиксировать нечего — QA — warn — [Как обновлять](../docs/15-maintenance/update-process.md).

## Stop conditions

Любой невыполненный `block` останавливает передачу заказчику. Отчёт, не прошедший валидатор, и
персональные данные в артефактах — безусловные блокеры: первый ломает доверие к содержимому, второй
создаёт юридический риск.
