# qa-execute — прогон

Тонкий роутер. Источник правды — `D:\Rabota\llm-qa-wiki`.

Фаза даёт факты. Провал без доказательства возвращается со статусом «не воспроизвелось» и обесценивает
работу.

## Requires

- Закрыта фаза `qa-design`: `_qa-cases.md` существует и непуст.
- Тестовые данные и доступы из `_qa-plan.md` получены.

## Сначала прочитай

- `pwsh D:\Rabota\llm-qa-wiki\tools\ask-wiki.ps1 "<область> доказательство прогон"`
- `docs\09-automation\evidence-collection.md` — иерархия доказательств и правила приватности.
- `docs\06-web-testing\devtools-console-network.md` — что снимать из инструментов разработчика.
- `docs\09-automation\playwright.md` — добыча фактов скриптами.
- `docs\09-automation\ui-evidence-runner.md` — сбор UI-доказательств одним прогоном по JSON-конфигу.
- `patterns\ui\computed-style-hover-proof.md` — типовой приём для UI-дефектов.
- `docs\05-defect-management\reproducibility.md` — как довести находку до воспроизводимости.

## Шаги

1. **Открой инструменты разработчика и держи открытыми весь прогон.** Ошибки консоли и коды ответов
   — самая дешёвая проверка с самой высокой отдачей.
2. **Начни со smoke.** Провал smoke означает, что сборку надо вернуть, а не продолжать прогон.
3. **Выполняй кейсы по порядку**, фиксируя результат каждого: `Pass`, `Fail`, `Blocked`, `N/A`.
   `Blocked` требует причины — обычно это отсутствующие данные или доступ.
4. **Выбери поверхность захвата до прогона.** Если встроенный браузер рантайма доступен, устойчивее
   выполняет пользовательские действия и поддерживает требуемый viewport, используй его для
   выполнения и PNG. Точную совместимость с Chrome проверяй отдельно и не приписывай снимку версию
   браузера, в котором он не был сделан. Если встроенный браузер недоступен либо нужен полностью
   воспроизводимый CLI-прогон, для функциональных сценариев используй
   `runner=functional-screenshots`, для UI-замеров — legacy-конфиг. Оба запускаются одной командой:
   `pwsh D:\Rabota\llm-qa-wiki\tools\ui-evidence\Invoke-UiEvidence.ps1 -Config <проект>\ui-cases.json -ProjectRoot <проект>`.
   Каждая лишняя навигация стоит десятки секунд, а на сайте с анти-бот защитой ещё и срывается.
   Точечный повтор отдельных кейсов — ключ `-Only`. Functional-прогон сначала пишет staging;
   `evidence\` заменяется только командой `-Approve <run-id>` после просмотра contact sheet.
   Частичная пересъёмка объединяется с ранее одобренными кейсами и сохраняет source run каждого PNG.
5. **Для каждого `Fail` собери доказательство** подходящего уровня. Приоритет — машинный замер:
   вычисленные стили, код и тело ответа сервера, результат проверки валидности поля. Запись экрана —
   для сценариев из нескольких шагов и плавающих дефектов.
6. **Следуй evidence policy проекта.** Для клиентского функционального отчёта значение по умолчанию
   — `all`: отдельный viewport-кадр на каждый Case ID. `failures` и `selected` допустимы, только если
   это явно зафиксировано в плане заказа.
   Основной кадр обязан показывать результат конкретного кейса. Для переходов снимай «до/после» или
   запись; для невидимых свойств добавляй машинное измерение. Одинаковая область страницы не является
   доказательством разных результатов.
7. **Именуй файлы доказательств** по идентификатору будущего дефекта, чтобы связь восстанавливалась
   без пояснений.
8. **Проверь приватность** каждого артефакта: ни персональных данных, ни учётных данных, ни
   содержимого чужих аккаунтов.
9. **Фиксируй фактическое окружение**, а не запланированное: браузер, версия, ОС, разрешение.
   Выбранные OSS-профили запускай через `$qa-toolkit`: сначала preflight, затем только разрешённый
   target. Запиши `result.json`, artifacts и hashes; `blocked`/`error` не маскируй.
10. **Артефакт.** Сохрани `_qa-run.md`: сессия и тестировщик, фактическое окружение, результат по
   каждому кейсу с комментарием, ссылки на доказательства. Файлы — в `evidence\`.

## Quality gate

- Каждый кейс из `_qa-cases.md` имеет результат.
- Каждый `Blocked` имеет причину.
- У каждого кейса есть доказательство, а не только словесное описание: `Pass` без снимка —
  утверждение без подтверждения.
- Основной PNG каждого Case ID визуально соответствует ожидаемому или фактическому результату
  кейса. Переходы имеют «до/после» или запись, невидимые свойства — машинный замер.
- Точных дубликатов основных PNG разных Case ID нет. Визуально похожие кадры вручную проверены на
  contact sheet и действительно доказывают разные результаты.
- **Имя файла начинается с Case ID:** `TC-001.png`, несколько кадров на кейс — `TC-001-2-hover.png`.
  Файлы, не привязанные к кейсу (журналы, замеры, разведка), с `TC-` не начинаются. Правило
  проверяется на фазе `qa-report` ключом `--evidence`, но соблюдается здесь — переименовывать
  задним числом дороже, чем сразу назвать верно.
- Комментарий к `Fail` описывает наблюдаемое, а не гипотезу о причине.
- Зафиксировано фактическое окружение.
- Для нового functional-прогона `evidence\data\screenshot-run.json` имеет approval `approved`, а
  фактический дисплей и viewport совпадают с окружением в отчёте.
- Для снимков встроенного браузера зафиксированы поверхность захвата, заданный viewport и фактический
  размер PNG; ручная проверка Chrome, если она требовалась, указана отдельно.
- Ни один артефакт не содержит персональных или учётных данных.

Вывод раннера (`signal`) — не вердикт. `Pass` и `Fail` ставятся по критериям `_qa-plan.md`:
иначе отчёт начнёт отражать пороги инструмента, а не требования заказа.
То же относится к toolkit findings, включая axe violations и incomplete: их вручную сопоставляет
тестировщик, а автоматический `clean` не доказывает WCAG compliance.

Встроенный/MCP-браузер допустим как предпочтительный ускоритель выполнения и захвата, когда он
доступен и устойчив. Он не является обязательной зависимостью: тот же критерий готовности должен
закрываться командным раннером в другом агентном рантайме.
