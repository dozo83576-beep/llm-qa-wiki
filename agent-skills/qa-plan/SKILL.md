# qa-plan — тест-план

Тонкий роутер. Источник правды — `D:\Rabota\llm-qa-wiki`.

Фаза превращает зафиксированный объект в план работ с проверяемыми критериями. Главная её функция —
защита от спора об объёме при сдаче.

## Requires

- Закрыта фаза `qa-intake`: `_qa-intake.md` существует и непуст.
- Прочитан `_qa-intake.md` целиком, включая раздел «вне скоупа».

## Сначала прочитай

- `pwsh D:\Rabota\llm-qa-wiki\tools\ask-wiki.ps1 "<тип объекта> тест-план критерии выхода"`
- `docs\04-documentation\test-plan.md` — состав документа.
- `docs\14-templates\test-plan-template.md` — заготовка.
- `docs\02-levels-and-types\index.md` — таблица выбора видов под свойства объекта.
- `docs\03-test-design\risk-based-testing.md` — распределение объёма по риску.
- `docs\02-levels-and-types\non-functional-overview.md` — перевод расплывчатых ожиданий в числа.
- Соответствующий playbook из `docs\13-playbooks\`.

## Шаги

1. **Выбери виды тестирования от свойств объекта**, а не по списку «что бывает». Для каждого запиши
   причину: свойство объекта, которое его требует. Вид без причины — либо лишние часы, либо
   непокрытый риск.
2. **Построй таблицу рисков** по `risk-based-testing.md`: вероятность × ущерб. Ущерб подтверди у
   заказчика — техническая критичность и бизнесовая расходятся.
3. **Распредели объём** по риску. Области с низким риском покрываются smoke и помечаются как
   проверенные поверхностно.
4. **Переведи нефункциональные ожидания в числа.** «Должно быть быстро» — не критерий. Нет чисел от
   заказчика — предложи свои и зафиксируй как согласованное допущение.
5. **Подбери чек-листы** из `checklists\` под тип объекта. Перечисли их поимённо: по ним потом
   считается покрытие.
6. **Задай entry и exit criteria.** Критерии выхода формулируй через severity — так они проверяемы
   без обращения к заказчику.
7. **Составь перечень тестовых данных** и запроси недостающее сейчас, а не в момент прогона.
   Для инструментальных сигналов выбери профили из `resources\qa-tool-catalog.yaml` и запиши точную
   версию, prerequisites, authorization, ожидаемый artifact и ограничение каждого профиля.
8. **Артефакт.** Сохрани `_qa-plan.md` по шаблону: объект, вне скоупа, окружение, виды с
   обоснованием, таблица рисков, выбранные чек-листы, entry и exit criteria, тестовые данные, оценка
   по областям, формат и срок результата.

Для веб-проектов пользователя разрешение ПК по умолчанию — `1920×1080`. Используй его для основной
desktop-среды и скриншотов, если заказчик или требования явно не задали другое разрешение. Выбранные
разрешение экрана и viewport фиксируй в матрице окружений и в фактическом прогоне.

## Quality gate

- Каждый выбранный вид тестирования обоснован свойством объекта из `_qa-intake.md`.
- Exit criteria содержат числа и проверяемые условия, а не «продукт работает стабильно».
- Нефункциональные ожидания выражены числами.
- Чек-листы перечислены поимённо.
- Перечень требуемых тестовых данных передан заказчику.
- В web-проекте основная desktop-среда использует `1920×1080` либо в плане зафиксировано другое
  разрешение из требований.
- План согласован письменно до начала прогона.
- Каждый выбранный toolkit-профиль привязан к риску и ожидаемому artifact; отсутствие runtime или
  разрешения заранее обозначено как `Blocked`, а не скрыто установкой или сменой target.

Проверяет: `pwsh D:\Rabota\llm-qa-wiki\tools\verify-qa-pipeline.ps1 -ProjectRoot <проект> -RequirePhase design`
