# qa-report — отчёт

Тонкий роутер. Источник правды — `D:\Rabota\llm-qa-wiki`.

Фаза производит то, за что платит заказчик. Формат согласован и проверяется посимвольно — отклонения
без согласования недопустимы.

## Requires

- Закрыта фаза `qa-defects`: `_qa-defects.md` существует и непуст.
- Доступны `_qa-cases.md`, `_qa-run.md`, `_qa-plan.md`.

## Сначала прочитай

- `docs\14-templates\xlsx-test-management.md` — спецификация формата поставки.
- `docs\14-templates\report-json-schema.md` — структура входного файла.
- `docs\14-templates\report-summary-template.md` — структура сопроводительного отчёта.
- `patterns\process\report-validator-gate.md` — почему валидатор независим от генератора.
- `checklists\qa-acceptance.md` — финальный гейт перед отправкой.

## Шаги

1. **Собери `_qa-report.json`** из артефактов предыдущих фаз по схеме. Источник правды — JSON:
   правки вносятся в него, отчёт пересобирается. Ручная правка XLSX затрётся следующей сборкой.
2. **Собери отчёт:**

   ```
   python D:\Rabota\llm-qa-wiki\tools\build-qa-report.py --input _qa-report.json --out outputs\QA_<Проект>_<дата>.xlsx
   ```

   Генератор отклонит данные с разрывом нумерации, `Fail` без дефекта или `Pass` с дефектом — читай
   сообщение и правь JSON, а не обходи проверку.
3. **Прогони валидатор с ожидаемыми итогами:**

   ```
   python D:\Rabota\llm-qa-wiki\tools\verify-qa-report.py outputs\QA_<Проект>_<дата>.xlsx --expect-pass N --expect-fail M --evidence evidence --summary outputs\ОТЧЁТ.md
   ```

   Числа бери из `_qa-run.md`. Расхождение означает ошибку в сборке JSON.
4. **Открой файл и посмотри глазами**: выпадающие списки работают, заливка Pass и Fail на месте,
   ссылки на доказательства кликабельны, текст не обрезан. Ширину столбцов и высоту строк
   генератор считает по содержимому — руками их не подгоняют, пересборка всё равно перезапишет.
5. **Собери `outputs\ОТЧЁТ.md`** по шаблону, указанному выше: что проверено с итоговой строкой
   `Итог: N Pass, M Fail.`, что работает, найденные дефекты. Границы скоупа, допущения и оценка по
   exit criteria в этот документ не идут — они остаются в `_qa-intake.md` и `_qa-plan.md`.
6. **Формулируй вывод через факты, а не как решение о релизе.** «Открыт один дефект `Minor`» —
   верно. «Релизить нельзя» — чужое решение.
   Toolkit findings переносить только после ручного сопоставления с кейсом и требованием; сырые
   `result.json` и engine status не превращать автоматически в QA verdict или Bug ID.
7. **Собери архив заказчику:**

   ```
   python D:\Rabota\llm-qa-wiki	ools\pack-delivery.py --project D:\Rabota\projects\<проект>
   ```

   Внутри — книга и каталог `Скриншоты\` с PNG, больше ничего. `ОТЧЁТ.md` в архив не кладётся:
   его текст идёт отдельным сообщением в поле «Ответ на отчёт». Журналы прогона и замеры тоже
   остаются снаружи — их читает команда.
8. **Пройди `checklists\qa-acceptance.md`** целиком перед отправкой.
9. **Артефакт.** `_qa-report.json` в корне проекта, XLSX и архив в `outputs\`.

## Quality gate

- Валидатор проходит без нарушений.
- Итоги Pass и Fail совпадают с `_qa-run.md` и с сопроводительным сообщением.
- Перелинковка на месте: `Case ID` и `Bug ID` на `Test Run`, `Related Case ID` и `Session ID` на
  `Bug Reports` — кликабельны и ведут на свою строку. Ссылки ставит генератор, руками их не правят.
- Поле `Tester` заполнено именем человека, который вёл заказ.
- Имя каждого доказательства начинается с Case ID, у каждого кейса свой снимок, и в строке дефекта
  стоят снимки её `Related Case ID`, а не всей группы. Проверяется ключом `--evidence`.
- Основной снимок каждого кейса показывает заявленный результат. Для динамики приложены состояния
  «до/после» или запись, для невидимых свойств — измерение; точные дубликаты основных PNG являются
  блокером сдачи, визуально похожие кадры просмотрены на contact sheet.
- Собран `outputs\ОТЧЁТ.md` по шаблону `docs\14-templates\report-summary-template.md`: что
  проверено с итогом `N Pass, M Fail`, что работает, найденные дефекты. Числа и идентификаторы
  сходятся с книгой — проверяется ключом `--summary`.
- Ни одна ячейка не обрезана и лишнего воздуха в ней нет: размеры посчитаны по содержимому.
  Короткие поля (идентификаторы, статусы, даты, `Environment`, `Attachments/Links`) стоят по
  центру, текстовые — влево и по нижнему краю. Раскладка по столбцам — в спецификации формата.
- Архив собран `pack-delivery.py`: каталог кадров называется `Скриншоты`, ничего кроме PNG в нём нет.
- Все `block` из `checklists\qa-acceptance.md` выполнены.
- В файле и доказательствах нет персональных и учётных данных.
- Оценка готовности сформулирована через критерии выхода.

Отчёт не отправляется заказчику без чистого прогона валидатора. Это безусловное правило.

## Тон

Перед сборкой перечитай книгу глазами заказчика: шаги описывают действия человека, выводы
сформулированы словами. Замеров в книге быть не должно — ни контраста в отношениях, ни размеров
в пикселях, ни значений css-свойств, ни кодов ответа сервера. Они живут в `_qa-plan.md` (пороги) и
`evidence/data/` (замеры), куда ведут ссылки отчёта. Исключение — колонка `Environment`, и та
коротко: браузер с версией и ОС. Правило целиком: в `docs\14-templates\xlsx-test-management.md`.
