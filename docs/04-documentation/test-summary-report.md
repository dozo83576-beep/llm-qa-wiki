# Отчёт о тестировании

Итоговый документ для заказчика. Отвечает на один вопрос: можно ли передавать продукт дальше и с
какими рисками.

## Когда использовать

- Завершение этапа или заказа.
- Приёмка.
- Промежуточная сдача, если этап длинный.

## Когда не использовать

- Вместо оперативной связи. О блокирующем дефекте сообщают сразу, а не через неделю в отчёте.

## Состав

Поставка — XLSX формата Test Management
([спецификация](../14-templates/xlsx-test-management.md)). Он самодостаточен: содержит кейсы, прогон
и дефекты со сквозной трассируемостью.

Сопроводительное сообщение при передаче содержит то, чего в таблице нет:

**Что проверено.** Объект, версия, окружение, границы скоупа. Явно — что осталось за границей.

**Итог прогона.** Числа: выполнено кейсов, Pass, Fail, Blocked. Они должны сходиться с содержимым
файла — расхождение подрывает доверие ко всему отчёту.

**Дефекты по severity.** Сколько `Critical`, `Major`, `Minor`, `Trivial`. Критичные перечисляются
поимённо с одной строкой сути.

**Оценка готовности.** Соотнесение с exit criteria из [тест-плана](test-plan.md):

> Критерии выхода не выполнены: открыт один дефект `Major` (BR-002 — пункт «Проекты» ведёт на
> главную). Остальные критерии закрыты.

Формулировка — о критериях, а не о решении. Решение о релизе принимает владелец продукта, см.
[роль тестировщика](../01-fundamentals/tester-role.md).

**Рекомендации** — отдельным разделом, без обязательства их выполнять.

### Короткая форма для заказа с биржи

Всё перечисленное выше — форма для приёмки внутри команды, где отчёт читает тот, кто принимает
решение о релизе. Заказчику с биржи сдаётся **короткая форма**: что делали, итог, что работает,
какие дефекты нашли. Границы скоупа, допущения и оценка относительно exit criteria в неё не входят
— они остаются в `_qa-intake.md` и `_qa-plan.md`, где их видно при разборе спора.

Причина простая: заказчик на бирже платит за час работы и читает документ один раз. Разделы,
которые он пролистает, снижают шанс, что он прочтёт те, что важны. Структура и правила —
в [шаблоне сопроводительного отчёта](../14-templates/report-summary-template.md).

## Метрики, которые имеют смысл

- Число выполненных кейсов и распределение по результату.
- Плотность дефектов по областям — показывает, где сосредоточен риск.
- Доля критичных дефектов от общего числа.

Метрики вроде «процент успешных тестов» без контекста бесполезны: 95% Pass при провале оплаты — плохой
результат.

## Частые ошибки

- Вывод «продукт готов к релизу» — это чужое решение.
- «Ошибок не обнаружено» вместо «в рамках заявленного скоупа дефектов не обнаружено».
- Числа в письме, не сходящиеся с файлом.
- Отсутствие раздела о непроверенном: после инцидента непроверенная область оказывается зоной
  ответственности тестировщика.
- Смешение дефектов и рекомендаций в одном списке.

## Проверка

```
python tools/verify-qa-report.py <отчёт>.xlsx --expect-pass N --expect-fail M
```

Дополнительно:

- итоги в сообщении сходятся с файлом;
- каждый критерий выхода имеет статус;
- раздел «вне скоупа» присутствует;
- рекомендации отделены от дефектов.
