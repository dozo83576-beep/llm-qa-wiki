# QA API

Маршрут для проверки сервиса напрямую: с документацией или без неё. Быстрее UI-проверок и находит то,
что интерфейс скрывает.

## Когда использовать

- Заказ на проверку бэкенда отдельно от интерфейса.
- Есть спецификация или коллекция запросов.
- Нужно проверить то, что недостижимо через интерфейс: права, серверную валидацию, состояния.

## Когда не использовать

- Без разрешения владельца на негативные и security-проверки.
- На продакшене с реальными данными при изменяющих действиях.

## Шаги

**1. Приём.** Зафиксировать базовый адрес, способ аутентификации, наличие спецификации, окружение
(обязательно не продакшен для изменяющих запросов), учётные записи всех ролей, разрешение на
негативные проверки.

**2. Карта эндпоинтов.** При наличии спецификации — из неё. Без спецификации — из панели сети
браузера: пройти интерфейс и собрать запросы, которые шлёт фронтенд. Второй способ работает почти
всегда.

**3. Позитивные сценарии.** По каждому эндпоинту: корректный запрос, ожидаемый код, ожидаемая
структура ответа. Фиксируется эталон структуры, если спецификации нет. См.
[контракт и схема](../08-api-testing/contract-and-schema.md).

До automation зафиксировать safety budget: test environment, разрешённые методы/endpoints, rate,
workers, synthetic data, cleanup и stop conditions. На production генеративные и изменяющие прогоны
не запускать.

**4. Коды ответов.** Штатные и ошибочные сценарии. Проверить, что валидация даёт 4xx, а не 500; что
несуществующий объект даёт 404; что неподдерживаемый метод даёт 405. См.
[коды ответов](../08-api-testing/http-and-status-codes.md).

**5. Валидация.** Отсутствующие обязательные поля, лишние поля, неверные типы, граничные значения,
очень длинные строки. По [эквивалентным классам](../03-test-design/equivalence-partitioning.md) и
[границам](../03-test-design/boundary-value-analysis.md).

**6. Состояния.** [Переходы состояний](../03-test-design/state-transition-testing.md), включая
запрещённые. API — единственное место, где запрещённый переход проверяется по-настоящему.

**7. Права доступа.** Чужой объект по прямому идентификатору, действие без прав, запрос без
аутентификации, действие старым токеном, попытка повышения привилегий через тело запроса. См.
[негативные и security-проверки](../08-api-testing/api-negative-and-security.md).

**8. Устойчивость.** Повторная отправка создающего запроса, ограничение частоты, одновременные
запросы на изменение одного объекта.

**9. Утечки.** Тела ошибок без трассировки и внутренних путей. Чувствительные данные не в параметрах
URL.

**10. Advanced contract checks.** Schemathesis — ограниченный schema-driven прогон; oasdiff —
baseline/candidate breaking diff; Pact — consumer/provider verification. Недоступные зависимости
заменять WireMock, а БД/брокеры — одноразовыми Testcontainers; затем обязателен разрешённый прогон с
реальной test dependency. См. [виртуализацию](../08-api-testing/service-virtualization.md).

**11. Отчёт.** Сборка XLSX. В шагах кейсов указываются метод, адрес и тело запроса — это делает их
воспроизводимыми.

## Частые ошибки

- Проверка только успешных ответов.
- Игнорирование структуры ошибочных ответов.
- Проверка прав только через интерфейс.
- Изменяющие запросы на продакшене.
- Кейсы без указания метода и тела запроса — невоспроизводимы.

## Проверка

- Каждый эндпоинт покрыт позитивным и негативным сценарием.
- Ни один пользовательский сценарий не даёт 500.
- Для каждой роли проверен доступ к чужому объекту.
- Проверена повторная отправка создающего запроса.
- Коллекция запросов сохранена в проекте, прогон воспроизводим.
