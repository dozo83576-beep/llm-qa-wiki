# Регресс перед релизом

Маршрут повторного прогона после изменений. Объём определяется зоной правок, а не желанием проверить
всё: полный регресс перед каждым релизом не окупается и потому не проводится.

## Когда использовать

- Перед выкладкой на продакшен.
- После исправления пакета дефектов.
- После обновления библиотек, CMS, платёжного модуля.

## Когда не использовать

- Вместо первичного тестирования новой функциональности. Регресс проверяет старое.

## Шаги

**1. Получить список изменений.** Что правили, какие дефекты исправлены, какие библиотеки обновлены.
Без этого объём определить нельзя, и регресс превращается в случайную выборку.

**2. Smoke.** 5–15 минут: открывается главная, работает авторизация, проходит ключевой сценарий, нет
ошибок в консоли. Провал — сборка возвращается, дальше не тестируем.

**3. Ретест исправленных дефектов.** По шагам из баг-репорта, на той сборке, где заявлено
исправление. Не «вроде работает», а точное повторение. См.
[жизненный цикл](../05-defect-management/defect-lifecycle.md).

**4. Проверка вокруг исправлений.** Правка ломает соседнее чаще, чем кажется. Для каждого
исправленного дефекта — проверка функциональности, использующей тот же код или тот же экран.

**5. Зона изменений.** Области, которые правили, и всё, что от них зависит.

**6. Сквозные элементы.** Шапка, подвал, меню, авторизация — ломаются чаще всего, потому что
присутствуют везде и правятся вскользь.

**7. Критичные для бизнеса сценарии.** Оплата, оформление заказа, отправка заявки, регистрация —
независимо от того, правили их или нет.

**8. Места прошлых дефектов.** Принцип скопления: где находили раньше, найдут снова. См.
[принципы](../01-fundamentals/testing-principles.md).

**9. Совместимость.** Smoke на остальных браузерах и на мобильном разрешении.

**10. Отчёт.** Что проверено, результаты ретеста, новые дефекты, оценка относительно exit criteria.

## Пополнение набора

После каждого пропущенного в прод дефекта в регрессионный набор добавляется проверка на него. Без
этого набор перестаёт находить новое — [парадокс пестицида](../01-fundamentals/testing-principles.md).

## Частые ошибки

- Регресс без списка изменений: проверяется наугад.
- Ретест без проверки области вокруг.
- Закрытие дефекта по слову разработчика.
- Пропуск сквозных элементов: их «недавно смотрели».
- Ретест на другой сборке, чем та, где заявлено исправление.

## Проверка

- Получен список изменений и исправленных дефектов.
- Smoke пройден до начала основного объёма.
- Каждый исправленный дефект прошёл ретест по исходным шагам.
- Проверена область вокруг каждого исправления.
- Сквозные элементы и критичные сценарии проверены независимо от зоны правок.
- Набор пополнен проверками на пропущенные ранее дефекты.
