# HTTP и коды ответов

Код ответа — самый быстрый способ отличить работающий сценарий от сломанного. Неверный код сам по
себе дефект: клиенты и поисковые системы принимают решения по нему, а не по тексту страницы.

## Когда использовать

- При любой проверке формы и запроса: смотреть код обязательно.
- При проверке обработки ошибок.
- При проверке SEO-поведения: 404 и редиректы.

## Когда не использовать

- Как единственный критерий. Ответ 200 с телом `{"error": "..."}` — тоже дефект, просто другого рода.

## Коды, которые проверяются чаще всего

| Код | Когда должен быть | Типовой дефект |
|---|---|---|
| 200 | успешное чтение | 200 на несуществующей странице вместо 404 |
| 201 | объект создан | 200 вместо 201 при создании |
| 204 | успех без тела | тело возвращается вопреки коду |
| 301 / 302 | постоянный / временный редирект | 302 там, где нужен 301 — теряется вес страницы |
| 400 | некорректный запрос | 500 вместо 400 на невалидных данных |
| 401 | не аутентифицирован | 200 с пустыми данными вместо 401 |
| 403 | аутентифицирован, но нет прав | 404 вместо 403 или наоборот |
| 404 | объект не найден | 200 с пустой страницей |
| 409 | конфликт состояния | 200 при повторной оплате |
| 422 | валидация не пройдена | 500 при ошибке валидации |
| 429 | слишком много запросов | отсутствие ограничения вообще |
| 500 | ошибка сервера | ошибка сервера на штатном сценарии |

**Главное правило:** 500 на любом пользовательском сценарии — дефект. Ошибка ввода должна давать
4xx, а не падение сервера.

## Методы

- `GET` не меняет состояние. Если удаление работает через `GET`, это дефект безопасности: ссылку
  можно вызвать со стороны.
- `POST` создаёт. Повторная отправка не должна создавать дубль — проверяется идемпотентность.
- `PUT` и `PATCH` изменяют, `DELETE` удаляет. Повторный `DELETE` уже удалённого даёт 404 или 204, но
  не 500.
- Неподдерживаемый метод на существующем адресе — 405, а не 500.

## Что ещё смотреть в ответе

- Тело ошибки объясняет причину, но не раскрывает внутренности: трассировка стека и SQL-запрос в
  ответе — дефект безопасности.
- Заголовки кэширования на страницах с личными данными запрещают кэширование.
- Время ответа фиксируется — основание для замечаний по производительности.

## Частые ошибки

- Проверка только текста на странице без кода ответа.
- Вывод «404 работает» по факту красивой страницы при коде 200.
- Игнорирование 500 на «редком» сценарии.
- Пропуск проверки повторной отправки.

## Проверка

- Для каждого штатного и ошибочного сценария зафиксирован код ответа.
- На несуществующем адресе подтверждён код 404.
- Ни один пользовательский сценарий не даёт 500.
- Повторная отправка формы проверена на создание дубля.
- Тело ошибки не содержит внутренней технической информации.
