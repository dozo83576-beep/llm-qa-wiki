# Виртуализация сервисов

Способ тестировать поведение при недоступной, нестабильной или дорогой зависимости, не отправляя
запросы в реальную внешнюю систему.

## Когда использовать

- Провайдер недоступен в CI или нужны редкие ответы, задержки и сбои.
- Нужна изолированная БД, очередь или другой реальный сервис на время теста.

## Когда не использовать

- Для окончательного доказательства совместимости с реальным провайдером.
- Если mock повторяет предположение команды, но не подтверждён контрактом или записью разрешённого
  тестового трафика.

## Как это делается

- WireMock: задать минимальные stubs по методу, пути, заголовкам и телу; добавить 4xx/5xx, delay,
  reset и проверку полученных запросов. Не записывать production-трафик с ПДн или секретами.
- Testcontainers: поднять одноразовую зависимость с закреплённым образом, дождаться readiness,
  передать приложению динамический адрес и гарантировать cleanup даже после падения теста.
- В обоих случаях хранить fixture рядом с тестом, указывать версию контракта и отдельно иметь хотя бы
  один разрешённый integration-прогон против реального test environment.

## Частые ошибки

- Mock всегда возвращает успех и скрывает retry, timeout и error mapping.
- Плавающий тег образа делает прогон невоспроизводимым.
- Общая контейнерная БД сохраняет состояние между тестами.

## Проверка

- Тест воспроизводит успех, отказ, задержку и malformed response.
- Stub проверяет существенные поля запроса, а контейнер стартует с чистым состоянием.
- Есть отдельное подтверждение, что fixture не разошёлся с реальным контрактом.
