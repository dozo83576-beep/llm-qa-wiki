# Проверка контракта и схемы

Контракт — договорённость о структуре запросов и ответов. Он служит
[оракулом](../01-fundamentals/test-oracle-and-limits.md): расхождение с ним доказуемо и не требует
спора о вкусах.

## Когда использовать

- Есть спецификация OpenAPI или описание формата.
- Фронтенд и бэкенд разрабатываются раздельно.
- Мобильное приложение: старые клиенты живут долго, ломать контракт нельзя.

## Когда не использовать

- Внутренний вызов, у которого один потребитель, меняющийся вместе с сервисом.

## Что проверять

**Структура ответа.**

- все обязательные поля присутствуют;
- типы соответствуют объявленным: число не приходит строкой;
- `null` там, где он не разрешён, — дефект;
- пустой список приходит как `[]`, а не как `null` или отсутствующее поле;
- вложенные объекты соответствуют своим схемам.

**Форматы.** Дата в объявленном формате и в объявленном часовом поясе. Денежные суммы в одной
единице: рубли или копейки, но последовательно. Идентификаторы одного типа во всех ответах.

**Обработка запроса.**

- отсутствующее обязательное поле даёт 400 или 422, а не 500;
- лишнее неизвестное поле игнорируется, а не ломает обработку;
- поле правильного типа, но недопустимого значения отклоняется;
- пустая строка и `null` различаются, если это имеет смысл.

## Обратная совместимость

Изменение, ломающее существующих потребителей, — дефект, даже если новая версия сама по себе
корректна:

- удаление поля из ответа;
- переименование поля;
- сужение типа: строка стала перечислением;
- новое обязательное поле в запросе;
- изменение смысла значения при том же имени.

Безопасные изменения: добавление необязательного поля в запрос, добавление поля в ответ, добавление
нового значения в перечисление — при условии, что клиент к этому готов.

Для мобильных приложений проверка обратной совместимости обязательна: см.
[установка и обновление](../07-mobile-testing/install-update-store.md).

## Как проверять

- При наличии OpenAPI — валидация ответа против схемы автоматически, а не глазами.
- Без спецификации — фиксация фактической структуры ответа как эталона и сравнение с ней при
  регрессе.
- Сравнение ответов до и после изменения — самый дешёвый способ поймать поломку контракта.

## Частые ошибки

- Проверка только успешного ответа: структура ошибки не описана и различается от эндпоинта к
  эндпоинту.
- Игнорирование типов: `"price": "100"` вместо числа ломает арифметику на клиенте.
- Пропуск пустых коллекций — частый источник падения клиента.
- Приёмка ломающего изменения без проверки старых клиентов.

## Проверка

- Ответы валидированы против схемы, если она есть.
- Проверены структуры ошибочных ответов, а не только успешных.
- Проверены пустые коллекции и необязательные поля.
- Для каждого изменения контракта проверена совместимость со старым клиентом.
