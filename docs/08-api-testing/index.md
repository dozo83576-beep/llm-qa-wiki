# Тестирование API

Проверка сервиса напрямую, минуя интерфейс. Дешевле и надёжнее UI-проверок: нет зависимости от
вёрстки, быстрее выполняется, точнее локализует причину.

- [HTTP и коды ответов](http-and-status-codes.md) — что должно возвращаться и когда.
- [Проверка контракта и схемы](contract-and-schema.md) — структура ответа как оракул.
- [Негативные и security-проверки API](api-negative-and-security.md) — то, что не проверить через
  интерфейс.

## Когда это доступно на заказе

Даже без документации API проверяется через панель сети браузера: запросы, которые шлёт фронтенд,
можно повторить и изменить. Это открывает проверки, недостижимые через интерфейс:

- отправка данных в обход клиентской валидации;
- запрещённые [переходы состояний](../03-test-design/state-transition-testing.md);
- доступ к чужим объектам подменой идентификатора;
- поведение при отсутствующих и лишних полях.

## Инструменты

Для разовых проверок хватает панели сети и повтора запроса из неё. Для набора проверок — любой
HTTP-клиент с сохранением коллекции; важно, чтобы коллекция сохранялась в проекте и прогон был
воспроизводим.

Автоматизация API-проверок делается тем же инструментом, что и UI, чтобы не плодить стеки, см.
[Playwright](../09-automation/playwright.md) — он умеет отправлять запросы без браузера.

## Что даёт наибольшую отдачу

1. Коды ответов на штатных и ошибочных сценариях.
2. Валидация на сервере при обходе клиентской.
3. Разграничение доступа: чужой объект по прямому идентификатору.
4. Структура ответа: обязательные поля на месте, типы соответствуют.
5. Идемпотентность: повторная отправка не создаёт дубль.
