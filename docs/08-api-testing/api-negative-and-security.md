# Негативные и security-проверки API

Проверки, недостижимые через интерфейс: он скрывает кнопки и валидирует поля. Сервер обязан
защищаться сам, потому что клиент подконтролен пользователю.

## Когда использовать

- Есть личный кабинет, роли, платные функции или персональные данные.
- Клиентская валидация выглядит единственной защитой.

## Когда не использовать

- **Без письменного разрешения владельца системы.** Проверки на чужом продакшене без согласования —
  не тестирование. Разрешение, границы и окно времени фиксируются до начала.
- На продакшене с реальными данными: нужен отдельный стенд.

## Разграничение доступа

Самая результативная группа проверок:

- **Чужой объект по идентификатору.** Войти пользователем A, взять из панели сети запрос вида
  `/api/orders/123`, подставить идентификатор заказа пользователя B. Доступ к чужим данным —
  дефект `Critical`.
- **Действие без прав.** Роль без права удаления отправляет запрос удаления напрямую. Кнопка скрыта —
  это не защита.
- **Запрос без аутентификации.** Тот же вызов без токена или cookie должен давать 401, а не данные.
- **Действие после выхода.** Старый токен перестаёт работать сразу, а не через час.
- **Повышение привилегий через данные.** Передача `"role": "admin"` в теле запроса на обновление
  профиля не должна приниматься.

## Валидация на сервере

- Значения за границей, отклонённые клиентом, отправляются напрямую: сервер обязан отклонить их тоже.
- Отсутствующие обязательные поля, лишние поля, неверные типы.
- Очень длинные строки — проверка на обрезание и на падение.
- Специальные символы в полях, попадающих в запросы к базе и в HTML: результат не должен
  интерпретироваться как код. Проверка ограничивается фиксацией факта, эксплуатация не выполняется.

## Устойчивость

- **Повторная отправка.** Двойная отправка платежа или заявки не создаёт дубль.
- **Ограничение частоты.** Много запросов подряд к форме входа или отправке кода должны упереться в
  429. Отсутствие ограничения — дефект: подбор пароля и рассылка SMS за счёт владельца.
- **Гонка.** Два одновременных запроса на списание с одного баланса.

## Утечки в ответах

- Трассировка стека, SQL-запрос, путь к файлу в теле ошибки.
- Персональные данные в ответах, где они не нужны: чужой email в списке заказов.
- Чувствительные данные в параметрах URL — попадают в логи сервера и историю браузера.

## Частые ошибки

- Проверка прав только через интерфейс.
- Проведение проверок без письменного разрешения.
- Нагрузка на проде при проверке ограничения частоты.
- Попытка эксплуатации найденной уязвимости вместо фиксации факта.

## Проверка

- Получено письменное разрешение с указанием границ и окна времени.
- Для каждой роли проверен доступ к чужому объекту по прямому идентификатору.
- Серверная валидация проверена в обход клиентской.
- Проверено ограничение частоты на форме входа.
- Тела ошибок проверены на утечку внутренней информации.
