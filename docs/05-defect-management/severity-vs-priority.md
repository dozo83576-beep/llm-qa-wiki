# Severity против priority

Две независимые шкалы. Severity — насколько сильно сломано; priority — насколько срочно чинить. Их
постоянно смешивают, из-за чего в отчёте появляются дефекты «Critical/Low», которые никто не может
интерпретировать.

## Когда использовать

- При оформлении каждого дефекта.
- При споре с разработчиком о срочности: спор почти всегда идёт о priority, а не о severity.
- При формулировке exit criteria в тест-плане.

## Когда не использовать

- Как единственное основание решения о релизе. Три `Minor` в оплате могут быть хуже одного `Major`
  в блоге.

## Severity — назначает тестировщик

Оценивается по влиянию на пользователя и данные, независимо от бизнес-планов.

| Severity | Критерий | Пример |
|---|---|---|
| `Critical` | функция недоступна, обходного пути нет; потеря или утечка данных | оплата не проходит; чужие заказы видны в личном кабинете |
| `Major` | функция работает неверно либо доступна с трудом; есть неудобный обходной путь | пункт меню ведёт не туда; форма отправляется только со второй попытки |
| `Minor` | отклонение заметно, но не мешает достичь цели | нет реакции на наведение; сообщение об ошибке общее вместо конкретного |
| `Trivial` | косметика | опечатка в подписи, смещение на 2 px |

Severity — измеримая величина, и она обосновывается фактом, а не ощущением. Основание берётся из
[таксономии](../../bug-taxonomy/index.md).

## Priority — назначает заказчик или менеджер

Учитывает бизнес-контекст: близость релиза, стоимость правки, видимость для клиентов, договорные
обязательства.

| Priority | Смысл |
|---|---|
| `High` | чинить до релиза |
| `Medium` | чинить в ближайшем цикле |
| `Low` | когда дойдут руки |

## Почему они независимы

- `Critical` / `Low` — падает функция, которой пользуются два человека раз в год. Сломано сильно,
  срочности нет.
- `Trivial` / `High` — опечатка в названии компании на главной. Сломано слабо, чинить сегодня.

Комбинация не является ошибкой. Ошибка — когда severity выставлена «на глаз» под желаемую срочность.

## Практика

- Тестировщик ставит severity и предлагает priority. Окончательный priority — за заказчиком.
- Спор о severity решается вопросом: что именно не может сделать пользователь и есть ли обходной
  путь.
- Дефект `Critical` сообщается сразу, не дожидаясь отчёта.
- В exit criteria указывается именно severity: «нет открытых `Critical` и `Major`» — это проверяемо
  без обращения к заказчику.

## Частые ошибки

- Завышение severity ради внимания. Обесценивает шкалу: через месяц `Critical` перестают читать.
- Занижение под давлением «до релиза два дня». Severity — факт, а не предмет переговоров; двигать
  надо priority.
- Одно поле вместо двух. Теряется различие между «сломано» и «срочно».
- Severity без обоснования: в отчёте нет фактического результата, по которому её можно проверить.

## Проверка

- У каждого дефекта заполнены обе шкалы.
- Severity подтверждается описанием фактического результата.
- Все `Critical` сообщены заказчику вне отчёта.
- Exit criteria в тест-плане сформулированы через severity.
