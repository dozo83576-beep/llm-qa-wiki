# Жизненный цикл дефекта

Статусы, через которые проходит дефект, и правила переходов. Значение имеет не сама схема, а то, кто
имеет право переводить дефект в каждый статус.

## Когда использовать

- Есть трекер задач и несколько участников.
- Заказчик спрашивает статус: «сколько ещё открыто».
- Дефект закрыли без исправления и надо понять, законно ли.

## Когда не использовать

- Разовый заказ с отчётом-таблицей и без трекера. Тогда достаточно двух состояний: найден и
  подтверждён исправленным.

## Статусы

Набор соответствует справочнику `StatusOptions` в
[формате отчёта](../14-templates/xlsx-test-management.md):

- **Open** — найден и оформлен, ждёт разбора.
- **In Progress** — взят в работу.
- **Fixed** — разработчик заявил исправление. Ещё не проверено.
- **Closed** — [ретест](../02-levels-and-types/smoke-regression-retest.md) подтвердил исправление.
- **Rejected** — отклонён: поведение штатное, либо вне скоупа, либо не воспроизводится.
- **Duplicate** — уже заведён, см. [триаж](triage-and-duplicates.md).

## Правила переходов

**Закрывает дефект только тестировщик.** `Fixed` ставит разработчик, `Closed` — тот, кто проверил.
Разработчик, закрывающий собственную правку, — типовой источник «починенных» дефектов в проде.

**Отклонение обосновывается.** `Rejected` без причины возвращается в `Open`. Допустимые причины:
поведение соответствует требованиям (со ссылкой), вне согласованного скоупа, не воспроизводится после
уточнения шагов.

**Ретест по шагам из репорта.** Не «посмотрел, вроде работает», а точное повторение сценария на
версии, где заявлено исправление. Отсюда требование к
[воспроизводимости](reproducibility.md).

**После ретеста — проверка вокруг.** Правка ломает соседнее чаще, чем кажется.

**Переоткрытие вместо нового дефекта.** Если после `Closed` проблема вернулась, дефект
переоткрывается: так видна история, а метрики не врут.

## Практика на разовом заказе

Без трекера цикл сжимается: дефекты попадают в отчёт со статусом «найден», заказчик передаёт их
разработчику, после исправлений заказывается отдельный этап ретеста. Этот этап оговаривается заранее
— иначе повторная проверка становится бесплатной работой.

## Частые ошибки

- Закрытие по слову разработчика без ретеста.
- `Rejected` без причины — дефект исчезает, проблема остаётся.
- Новый дефект вместо переоткрытия: статистика показывает ложное улучшение.
- Ретест на другой сборке, чем та, где заявлено исправление.
- Отсутствие проверки области вокруг исправления.

## Проверка

- Каждый `Closed` подтверждён ретестом по исходным шагам.
- Каждый `Rejected` имеет письменное основание.
- После ретеста проверена смежная функциональность.
- Возвращённые дефекты переоткрыты, а не заведены заново.
