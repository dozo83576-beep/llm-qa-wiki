# Техники тест-дизайна

Способы получить проверки из требований, а не выдумать их. Каждая техника решает одну задачу:
сократить перебор, не потеряв покрытие.

## Техники и когда какая

| Техника | Задача | Типовое применение |
|---|---|---|
| [Эквивалентные классы](equivalence-partitioning.md) | сократить число значений | любое поле ввода |
| [Граничные значения](boundary-value-analysis.md) | поймать ошибки на краях диапазона | длина, цена, количество, даты |
| [Таблицы решений](decision-table-testing.md) | покрыть комбинации условий | скидки, тарифы, доступ по роли |
| [Диаграммы состояний](state-transition-testing.md) | покрыть переходы | статус заказа, сессия, корзина |
| [Попарное тестирование](pairwise-testing.md) | сжать комбинаторный взрыв | фильтры, настройки, матрица сред |
| [Предугадывание ошибок](error-guessing.md) | добрать то, что техники пропускают | опыт и таксономия дефектов |
| [Исследовательское](exploratory-testing.md) | найти неизвестное | нет ТЗ, мало времени |
| [Risk-based](risk-based-testing.md) | расставить приоритет | всегда при ограниченном бюджете |

## Порядок применения

1. **Risk-based** сверху: определить, где сосредоточить усилия.
2. **Эквивалентные классы плюс граничные значения** для каждого поля — базовый минимум.
3. **Таблицы решений или диаграммы состояний**, если есть комбинации условий или статусы.
4. **Попарное**, если комбинаций слишком много для полного перебора.
5. **Предугадывание ошибок и исследовательское** — добор поверх формального набора.

Первые четыре дают воспроизводимый набор, который можно передать другому человеку. Последние два
зависят от опыта и в отчёте оформляются как отдельная сессия.

## Как это выглядит в артефакте

В `_qa-cases.md` у каждого кейса указывается применённая техника. Это не бюрократия: техника
объясняет, почему выбрано именно это значение, и позволяет проверить полноту покрытия.

Кейс без техники — обычно кейс наугад. Такие набираются вокруг happy path и пропускают ветки ошибок.

## Проверка покрытия

- Для каждого поля есть представитель каждого эквивалентного класса.
- Для каждого числового и строкового ограничения проверены границы.
- Для каждого статуса объекта проверены допустимые переходы и хотя бы один недопустимый.
- Каждый пункт выбранных чек-листов либо покрыт кейсом, либо помечен как непокрытый с причиной.
