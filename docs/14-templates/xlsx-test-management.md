# Спецификация XLSX Test Management

Формат итогового отчёта, который получает заказчик. Согласован и проверен на реальной сдаче —
отклонения от этого формата не допускаются без согласования.

## Когда использовать

- Любой заказ, завершающийся отчётом. Это формат поставки по умолчанию.

## Когда не использовать

- Заказчик явно потребовал другой формат. Тогда формат фиксируется в тест-плане до начала работ.

## Состав книги

Четыре листа в строго заданном порядке. Порядок и имена проверяются валидатором.

| Лист | Состояние | Назначение |
|---|---|---|
| `Data` | **скрытый** | справочники для выпадающих списков |
| `Test Cases` | видимый | тест-кейсы, 7 колонок |
| `Test Run` | видимый | прогон, 8 колонок |
| `Bug Reports` | видимый | дефекты, 13 колонок |

Листа `Evidence` **нет**, изображения в книгу не встраиваются. Доказательства идут ссылками.

## Справочники на листе `Data`

Оформляются именованными диапазонами — так выпадающие списки работают в любой версии Excel:

- `ResultOptions`: Pass, Fail, Blocked, N/A
- `SeverityOptions`: Critical, Major, Minor, Trivial
- `PriorityOptions`: High, Medium, Low
- `StatusOptions`: Open, In Progress, Fixed, Closed, Rejected, Duplicate

## Шапки

Двуязычные, в две строки: английский термин, перенос строки, русский перевод в скобках. Текст шапок
меняться не должен — валидатор сверяет его посимвольно.

`Test Cases`: Case ID, Title, Preconditions, Steps, Expected Result, Postconditions, Priority.

`Test Run`: Session ID, Date, Session Name, Tester, Case ID, Result, Comment, Bug ID.

`Bug Reports`: Bug ID, Title, Related Case ID, Session ID, Preconditions, Error Step, Expected Result,
Actual Result, Severity, Priority, Environment, Attachments/Links, Date Reported.

## Правила заполнения

**Нумерация.** Кейсы — сплошная с `TC-001`. Сессия — `TR-001`. Дефекты — `BR-001`.

**Трассируемость.** Проверяется механически:

- `Test Run` покрывает все кейсы в том же порядке;
- каждый `Fail` ссылается на существующий `Bug ID`;
- у каждого `Pass` поле `Bug ID` пустое;
- каждый дефект связан хотя бы с одним `Fail`.

**Раскладка дефекта.** Один дефект, проявившийся на нескольких элементах, раскладывается построчно:
`Bug ID` и `Title` — только в первой строке группы, дальше по строке на каждый затронутый элемент со
своим `Related Case ID` и своим шагом.

**Перелинковка.** Идентификаторы кликабельны и ведут на свою строку в другом листе:

| Лист | Колонка | Куда ведёт |
|---|---|---|
| `Test Run` | `Case ID` | строка кейса на `Test Cases` |
| `Test Run` | `Bug ID` | строка объявления дефекта на `Bug Reports` |
| `Bug Reports` | `Related Case ID` | строка кейса на `Test Cases` |
| `Bug Reports` | `Session ID` | `'Test Run'!A2` — там и только там проставлен номер сессии |

Ссылки ставит `tools/build-qa-report.py` и проверяет `tools/verify-qa-report.py`. **Руками их не
правят.** В первом отчёте, размеченном вручную, три ссылки из четырнадцати вели на служебный лист
`Data`, а одной не было вовсе: битую ссылку в книге не видно, она обнаруживается только по клику.

**Tester.** Поле заполняется именем человека, который вёл заказ, а не безличным «QA-инженер»: отчёт
подписан тем, кто отвечает за результат. Умолчание задано в генераторе константой `DEFAULT_TESTER`,
значение из JSON его перекрывает. Пустое поле валидатор не пропускает.

**Шаги** — нумерованным списком внутри одной ячейки, каждый шаг с новой строки.

**Язык** русский. Элементы интерфейса в «ёлочках». Ожидаемый результат измерим.

**Тон — человеческий, а не приборный.** Отчёт читает заказчик, а не разработчик: он должен
увидеть, что делал человек и что из этого вышло. Шаги описывают действия глазами и руками —
«навести курсор и подержать секунду», а не «снять вычисленные стили и сравнить попиксельно».
Вывод формулируется словами: «текст читается хорошо, белые буквы на тёмном фоне шапки не
сливаются». Замеров в книге нет вообще — ни контраста в отношениях, ни размеров в пикселях, ни
долей изменившихся точек, ни значений css-свойств.

Числа при этом никуда не деваются, они просто лежат не здесь:

| Где | Что там |
|---|---|
| `_qa-plan.md` | пороги, по которым ставился вердикт: контраст, размер зоны, длительность анимации |
| `evidence/data/` | сами замеры: вычисленные стили, попиксельные сравнения, геометрия, коды ответов |
| Книга отчёта | что делал человек и что он увидел, плюс ссылки на файлы выше |

Так отчёт читается без словаря, а дефект остаётся доказуемым: на спор «у нас всё видно»
открывается файл замеров. Исключение одно — колонка `Environment`: там нужна техника, иначе дефект
не воспроизвести. Но коротко: **браузер с версией и ОС**, например «Chrome 150, Windows 10 Home».
Разрешение, локаль и заголовки запроса в ячейку не идут — их место в `_qa-plan.md`, раздел
окружения.

Кодов ответа в тексте кейсов, прогона и дефектов нет: вместо «HTTP 200» пишется «страница выдачи
открылась без ошибок», вместо «сервер вернул 500» — «страница не открылась». Сам код остаётся в
машиночитаемом журнале прогона.

**Доказательства** — ссылками в `Attachments/Links`, кликабельными.

**Имя файла доказательства начинается с Case ID:** `TC-001.png`, при нескольких кадрах на кейс —
`TC-001-2-hover.png`. В строке дефекта стоят снимки **её собственного** `Related Case ID`, а не
всей группы: иначе строка про `TC-021` ссылается на кадры соседних кейсов, и разработчик открывает
не тот экран. Файлы, общие для всего дефекта — журнал прогона, замеры — попадают в каждую строку.
Правило целиком: [сбор доказательств](../09-automation/evidence-collection.md).

## Оформление

Шапка: заливка `#DBE5F1`, жирный 11 pt, по центру, перенос текста. Тело: 10 pt, выравнивание по
верху, перенос текста. Закреплена первая строка. Умные таблицы с автофильтром. Выпадающие списки на
Priority, Result, Severity — с блокировкой постороннего ввода. Условная заливка `Result`:
Pass `#C6EFCE`, Fail `#FFC7CE`, Blocked `#FFEB9C`, N/A `#D9E1F2`. Формат дат `yyyy-mm-dd hh:mm`.

## Сборка

```
python tools/build-qa-report.py --input _qa-report.json --out outputs/QA_Проект_2026-07-30.xlsx
```

## Проверка

```
python tools/verify-qa-report.py outputs/QA_Проект_2026-07-30.xlsx --expect-pass 10 --expect-fail 5
```

Валидатор независим от генератора: он читает готовый файл. Ноль нарушений — обязательное условие
передачи заказчику.

## Частые ошибки

- Правка шапок «для красоты» — файл перестаёт проходить валидатор.
- Схлопывание дефекта в одну строку с перечислением элементов в тексте: теряется трассируемость.
- Встраивание скриншотов в книгу вместо ссылок.
- Отправка файла без прогона валидатора.
