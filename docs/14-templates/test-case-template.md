# Шаблон тест-кейса

Заготовка для `_qa-cases.md`. Поля соответствуют колонкам листа `Test Cases` в
[формате отчёта](xlsx-test-management.md), поэтому переносятся в JSON без переработки.

## Когда использовать

- Фаза `qa-design` для всего, что идёт в отчёт заказчику.

## Когда не использовать

- Проверки, остающиеся внутри исследовательской сессии — для них достаточно
  [чек-листа](../04-documentation/checklist-vs-test-case.md).

## Шаблон

```markdown
### TC-0NN — <Область>: <что проверяется>

- **Техника:** <эквивалентные классы / границы / таблица решений / ...>
- **Покрывает:** <пункт чек-листа или требование>
- **Приоритет:** High | Medium | Low

**Предусловия**
<общая стартовая страница проекта: полный URL и локаль, ПК или мобильное устройство/эмуляция,
авторизация, наличие данных; для публичного веб-сайта по умолчанию открыта главная страница>

**Шаги**
1. <на стартовой странице найти и нажать точный элемент навигации>
2. <дождаться открытия целевой страницы или изменения состояния>
3. <выполнить целевое действие с конкретными данными, если оно требуется>
4. <проверить наблюдаемый результат по названным признакам>

**Ожидаемый результат**
<измеримый результат: конкретный текст, URL, наблюдаемое изменение>

**Постусловия**
<состояние системы после>
```

## Заполненный пример

```markdown
### TC-015 — Регистрация: пароль короче минимума

- **Техника:** граничные значения
- **Покрывает:** валидация обязательных полей (чек-лист функционального веба)
- **Приоритет:** High

**Предусловия**
Открыта форма регистрации. Используется уникальный валидный email.

**Шаги**
1. Ввести уникальный валидный email.
2. Ввести пароль из 4 символов.
3. Повторить пароль.
4. Нажать «Зарегистрироваться».

**Ожидаемый результат**
Появляется сообщение о минимуме 6 символов. Регистрация отклоняется, аккаунт не создаётся.

**Постусловия**
Форма остаётся открытой, аккаунт не создан.
```

## Правила

- Нумерация сплошная с `TC-001`. Разрыв — отчёт не пройдёт валидатор.
- Один кейс — одна проверка.
- В предусловиях веб-кейса указан полный URL, включая локаль: например,
  «Главная страница https://example.com/ru открыта на ПК».
- Для веб-проекта в предусловиях используется согласованная общая стартовая страница, по умолчанию
  главная. Путь от неё до целевого раздела описывается в шагах. Прямой URL целевого раздела допустим
  как предусловие только в кейсе, который специально проверяет открытие deep link.
- Пишется «на мобильном устройстве», а не «на мобильной ширине»; браузерная эмуляция явно
  называется эмуляцией и содержит viewport.
- В каждом кейсе не менее двух содержательных нумерованных шагов; переход, действие и наблюдение не
  склеиваются в один шаг.
- Шаги описывают действия, а не намерения.
- Каждый шаг называет элемент, действие и при необходимости введённые данные; переход и ожидаемая
  реакция описываются отдельно. Формулировки «перейти на страницу» и «проверить результат» без
  маршрута и признаков результата не проходят quality gate.
- Данные задаются правилом генерации, а не конкретным значением, если значение исчерпаемо.
- Элементы интерфейса — в «ёлочках».

## Частые ошибки

- Ожидаемый результат «работает корректно».
- Несколько проверок в одном кейсе.
- Отсутствие поля «Техника» — кейс, вероятно, взят наугад.
- Предусловие без полного URL или локали.
- Целевая страница подставлена в предусловие вместо воспроизводимого пути от стартовой страницы.
- Пропущен пункт меню, ссылка или кнопка, через которые пользователь доходит до целевого экрана.
- Один общий шаг вместо воспроизводимой последовательности.
- Отсутствие постусловий: следующий кейс падает на непредсказуемом состоянии.

## Проверка

- Кейс выполнен другим человеком с тем же результатом.
- Нумерация сплошная.
- В предусловиях указан полный URL и выбранная локаль.
- Для веб-кейса указан общий вход, а в шагах — полный путь до целевого экрана.
- В кейсе не менее двух содержательных шагов.
- У каждого кейса указана техника и покрываемый пункт.
- Ожидаемый результат содержит конкретику.
