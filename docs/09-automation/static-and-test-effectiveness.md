# Статические проверки и эффективность тестов

Практика для заказа, где доступен исходный код: сначала дешёвые проверки без запуска продукта,
затем генерация входов и проверка способности тестов замечать намеренные изменения.

## Когда использовать

- Код и команда сборки доступны, а найденные проблемы можно вернуть разработчикам.
- Нужна ранняя проверка типов, правил API, потенциальных ошибок и качества unit-тестов.

## Когда не использовать

- Есть только публичный интерфейс или бинарная сборка.
- Как замену runtime, integration, security и пользовательским проверкам.

## Как это делается

1. Зафиксировать язык, штатную команду lint/type-check и конфигурацию репозитория. Не включать новые
   правила массово без согласования: это создаёт шум и меняет baseline.
2. Запустить formatter в check-режиме, linter, type-checker и анализ зависимостей. Сохранить точную
   команду, версию, exit code и найденное правило.
3. Для чистых функций и парсеров описать свойства: round-trip, идемпотентность, монотонность,
   сохранение инварианта. Property-based тест генерирует множество примеров; упавший пример
   минимизируется и сохраняется как regression case.
4. Mutation testing запускать только на ограниченном модуле: инструмент меняет условие или значение,
   а тесты должны упасть. Выживший mutant означает непроверенную ветку либо слабый oracle, но не
   автоматически дефект продукта.
5. Сначала улучшить тесты вокруг критичных выживших mutants, затем повторить ограниченный прогон.

## Частые ошибки

- Считать отсутствие предупреждений доказательством корректности.
- Добавлять случайные property-based входы без бизнес-инварианта.
- Гнаться за mutation score целиком, игнорируя эквивалентные mutants и стоимость прогона.

## Проверка

- Команды повторяемы на чистом checkout и версии инструментов закреплены.
- Каждый property-based тест проверяет сформулированное свойство.
- Для mutation run сохранены scope, baseline tests, survived/killed и принятое решение.
