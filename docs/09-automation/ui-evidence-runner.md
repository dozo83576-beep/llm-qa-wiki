# Раннер UI-доказательств: один прогон вместо скрипта на каждый кейс

`tools/ui-evidence/` снимает доказательства по всем UI-кейсам заказа за одну навигацию и кладёт
результат в `evidence/` и `evidence/data/ui-evidence.json`. Кейсы описываются JSON-конфигом, а не
кодом: писать скрипт под каждый заказ не нужно.

## Когда использовать

- Заказ на UI или юзабилити: ховер, выпадающие списки, читаемость текста, доступность с клавиатуры.
- Объект под анти-бот защитой, где каждая навигация стоит 40–90 секунд и иногда срывается.
- Нужен повторный прогон после исправлений: те же кейсы, та же команда, сравнимые числа.

## Когда не использовать

- Проверка бизнес-логики и сценариев из многих шагов: раннер снимает состояния элементов, а не
  пользовательские маршруты.
- Заказ на API или мобильное приложение.
- Единственная разовая проверка одного элемента — быстрее посмотреть глазами.

## Как это делается

1. **Проверить среду:**

   ```
   pwsh tools/ui-evidence/Invoke-UiEvidence.ps1 -Check
   ```

   Скрипт сам находит Node, модуль `playwright` и браузер, подставляет `NODE_PATH`.

2. **Описать кейсы.** Копия `tools/ui-evidence/config.example.json` в каталог проекта как
   `ui-cases.json`. Один `id` — один кейс из `_qa-cases.md`. Типы проверок:

   | `check` | Что снимает | Ключевые поля |
   |---|---|---|
   | `hover` | стили в покое / под курсором / после ухода вместе с `::before` и `::after`, попиксельное сравнение области, длительность перехода | `selector` |
   | `dropdown` | способ раскрытия, состав и геометрия блока, перекрытые и ушедшие за экран пункты, достижимость нижнего пункта курсором, способы закрытия | `trigger`, `panel`, `itemSelector`, `closeButton`, `openBy`, `closeByTriggerClick` |
   | `esc` | закрывается ли раскрытый блок клавишей `Esc` | `trigger`, `panel`, `openBy` |
   | `readability` | типографика, контраст по фактическим пикселям, размер зоны, обрезка текста | `selector`, `hitAreaSelector` |
   | `tab-order` | остановки фокуса при обходе области клавишей `Tab`, видимость фокуса | `within`, `maxStops`, `expectStops` |
   | `focus-opens` | раскрывается ли блок, когда триггер получает фокус | `trigger`, `panel` |
   | `tab-inside` | доходит ли фокус до полей внутри раскрытого блока | `trigger`, `panel`, `presses`, `expectFocusOn` |

3. **Запустить прогон:**

   ```
   pwsh tools/ui-evidence/Invoke-UiEvidence.ps1 -Config <проект>\ui-cases.json -ProjectRoot <проект>
   ```

   Повторить отдельные кейсы: `-Only TC-001,TC-004`.

4. **Посмотреть снимки.** Курсор в снимок страницы браузер не пишет — его рисует операционная
   система, поэтому раннер дорисовывает указатель сам, накладкой поверх страницы. Накладка ставится
   только на время съёмки и в замеры не попадает: снимки для попиксельного сравнения снимаются до
   неё. У ховер-кейсов дополнительно собирается склейка `<id>-3-compare.png` — увеличенный фрагмент
   «до наведения» и «под курсором» друг под другом. На снимке всей шапки тонкое подчёркивание или
   смена оттенка теряются, на склейке видны.

5. **Разобрать `evidence/data/ui-evidence.json`.** У каждого кейса есть блок `signal` — короткая
   выжимка: есть ли реакция на экране, помещается ли блок в окно, проходит ли контраст.
   **Это не вердикт.** `Pass` или `Fail` ставит тестировщик по критериям тест-плана.

## Частые ошибки

- Считать `signal` вердиктом. Раннер не знает критериев заказа: 12.75 px кегля он покажет, а
  решение «допустимо или нет» принимается по тест-плану.
- Прогонять кейсы по одному «чтобы посмотреть». Каждый запуск — новая навигация и новая анти-бот
  проверка; для точечного повтора есть `-Only`.
- Держать конфиг в вики. Селекторы принадлежат заказу и живут в каталоге проекта.
- Забыть, что состояние страницы переносится между кейсами. Раннер закрывает открытые блоки перед
  каждым кейсом и перезагружает страницу, если блок не закрылся, но нестандартные состояния лучше
  разводить порядком кейсов в конфиге.

## Проверка

- `-Check` показывает версию `playwright`, путь к браузеру и профиль — до прогона, а не после сбоя.
- Заведомо неверный селектор даёт `Blocked` с причиной и код возврата 2, а не «зелёный» результат:
  раннер отличает «панели нет в DOM» (ошибка конфига) от «панель есть, но не раскрывается» (факт о
  системе).
- В `meta` каждого прогона записаны URL, HTTP-код, число навигаций, длительность, браузер, профиль
  и User-Agent — прогон воспроизводим.
