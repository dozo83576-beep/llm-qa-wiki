# Тестирование с опорой на observability

Корреляция тестового шага с trace и логом помогает локализовать сбой, не превращая телеметрию в
хранилище клиентских или персональных данных.

## Когда использовать

- Test environment экспортирует traces/logs и команда дала тестировщику read-only доступ.
- Один пользовательский шаг проходит через несколько сервисов.

## Когда не использовать

- Если доступ к observability не согласован или содержит реальные ПДн.
- Как замену проверке результата: «trace без ошибок» не доказывает правильный ответ пользователю.

## Как это делается

1. На старт прогона создать синтетический `qa.run_id`; на сценарий — `qa.case_id` без имени клиента,
   email, телефона, токена и иных данных пользователя.
2. Передать корреляцию разрешённым заголовком тестового окружения или span attribute. Сохранить
   `trace_id` из ответа/телеметрии рядом с фактическим результатом.
3. Искать trace по `qa.run_id`, проверять status, latency, retries и ошибочный span; в баг-репорт
   помещать только безопасный `trace_id` и время.
4. Baggage распространяется между процессами: ПДн, секреты, URL с токенами и содержимое запроса в
   baggage запрещены. Установить allowlist ключей и срок хранения.

## Частые ошибки

- Использовать email или order id реального пользователя как correlation id.
- Публиковать полное тело span/log в общем отчёте.
- Делать вывод о причине только по красному span без проверки результата и логов зависимости.

## Проверка

- По `qa.run_id` находится ровно нужный тестовый прогон, а `trace_id` ведёт к нужному запросу.
- Allowlist телеметрии не содержит ПДн и секретов.
- Баг воспроизводим без доступа к закрытому observability-интерфейсу.
