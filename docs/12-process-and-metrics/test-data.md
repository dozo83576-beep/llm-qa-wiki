# Тестовые данные

Подготовка, изоляция и очистка данных для проверок. Плохо организованные данные — частая причина
несостоявшегося прогона: половина кейсов помечается `Blocked` из-за отсутствия подходящих записей.

## Когда использовать

- Проверки требуют определённого состояния: заказы в разных статусах, роли, товары с разными
  свойствами.
- Прогон повторяется: регресс, ретест, автотесты.

## Когда не использовать

- Разовая проверка публичных страниц без авторизации.

## Что нужно подготовить

Список составляется на этапе [тест-плана](../04-documentation/test-plan.md), а не в момент прогона:

- учётные записи всех ролей, включая заблокированную;
- объекты во всех значимых статусах — по
  [диаграмме состояний](../03-test-design/state-transition-testing.md);
- граничные записи: товар с нулевым остатком, максимально длинное название, пустой список;
- данные для негативных проверок: занятый email, недействительная карта;
- доступ к почтовому ящику для проверки писем;
- реквизиты платёжной песочницы.

Отсутствие любого пункта выясняется в момент прогона и останавливает работу.

## Принципы

**Изоляция.** Кейс не зависит от данных, созданных другим кейсом. Иначе прогон в другом порядке даёт
другой результат, а параллельный запуск ломается.

**Уникальность.** Значения, которые система считает уникальными, генерируются с отметкой времени.
Жёстко зашитый email работает ровно один раз.

**Самодостаточность.** Кейс сам создаёт нужное состояние или явно перечисляет его в предусловиях. Так
он воспроизводится на чистой системе.

**Очистка.** Созданное убирается после прогона. Накопление тестовых заказов искажает выдачу, ломает
статистику и попадает в отчёты заказчика.

**Ненастоящесть.** Данные заведомо вымышленные, см. [персональные данные](../11-security-accessibility/personal-data.md).
Тестовый заказ на реальный адрес с реальным телефоном приводит к звонку живому человеку.

## Практика на заказе

- Перечень требуемых данных передаётся заказчику до начала работ вместе с запросом доступов.
- Если тестовой среды нет и проверки идут на продакшене, это фиксируется в тест-плане как риск, а
  создаваемые объекты помечаются узнаваемым префиксом и удаляются после.
- Список созданных объектов ведётся по ходу — по памяти в конце вспомнить не удаётся.

## Частые ошибки

- Подготовка данных в момент прогона: время уходит, часть кейсов остаётся `Blocked`.
- Зависимость кейсов друг от друга по данным.
- Тестовые заказы, оставшиеся в системе после сдачи.
- Реальные контакты в тестовых записях.
- Использование одной учётной записи для всех ролей.

## Проверка

- Перечень тестовых данных составлен на этапе плана и получен до начала прогона.
- Кейсы проходят при запуске в произвольном порядке.
- Уникальные значения генерируются, а не зашиты.
- Созданные объекты удалены или переданы списком.
- Ни одна тестовая запись не содержит реальных контактов.
