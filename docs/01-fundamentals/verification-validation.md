# Verification и validation

Два разных вопроса, которые постоянно смешивают. Verification: «продукт соответствует требованиям?»
Validation: «продукт решает задачу пользователя?» Пройти первое и провалить второе — обычное дело.

## Когда использовать

- При приёмке: заказчик оценивает validation, тест-кейсы покрывают verification.
- Когда реализовано «по ТЗ», а заказчик недоволен — почти всегда это разрыв между ними.
- При работе без формальных требований: validation становится единственной опорой.

## Когда не использовать

- Как повод расширять скоуп в одностороннем порядке. Расхождение с ожиданиями пользователя
  фиксируется как замечание и обсуждается, а не чинится молча.

## Как это делается

**Verification** — сверка с зафиксированным источником:

- макет против реализации: положение элементов, отступы, состояния;
- ТЗ против поведения: перечисленные сценарии работают;
- спецификация API против ответов сервиса.

Результат бинарен: соответствует или нет. Именно из verification получаются тест-кейсы с
однозначным ожидаемым результатом.

**Validation** — проверка пригодности:

- пользователь достигает цели за разумное число шагов;
- сообщения об ошибках объясняют, что делать;
- сценарий целиком проходится без внешней подсказки.

Результат оценочный, поэтому его нужно подкреплять: ссылкой на гайдлайн, замером, записью
прохождения сценария.

## Практика на веб-заказах

Типовой разрыв: форма валидирует поля строго по ТЗ (verification пройдена), но при ошибке
показывает «Ошибка 422» вместо указания на проблемное поле — пользователь не может продолжить.
Формально дефекта нет, фактически сценарий не работает.

Такие находки оформляются как дефекты со ссылкой на UX-критерий из
[чек-листа UX](../../checklists/ux-experience.md), а не на ТЗ. Severity обычно `Minor` или `Major`
в зависимости от того, блокирует ли это целевое действие.

## Частые ошибки

- Отчёт только с verification: «всё по макету», хотя ключевой сценарий не проходится.
- Validation без опоры: «неудобно» — не дефект. «Кнопка отправки за пределами первого экрана на
  360 px, целевое действие не видно без прокрутки» — дефект.
- Смешение в одном баг-репорте: несоответствие макету и претензия к удобству — это два разных бага
  с разной severity и разными адресатами.

## Проверка

- Каждый acceptance criterion из приёмки имеет статус.
- Ключевые пользовательские сценарии пройдены целиком, а не по отдельным экранам.
- Для каждого замечания по validation указан источник критерия.
