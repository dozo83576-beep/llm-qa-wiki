# Уровни и виды тестирования

Три независимые оси классификации. Их регулярно смешивают, из-за чего в тест-планах появляются
строки вроде «функциональное и регрессионное тестирование» — как будто это альтернативы.

- **Уровень** — на каком слое системы: [уровни тестирования](test-levels.md).
- **Вид** — что именно проверяем: функциональность или характеристики качества.
- **Цель прогона** — зачем запускаем набор: [smoke, регресс, ретест](smoke-regression-retest.md).

Одна проверка имеет значение по каждой оси одновременно: системный уровень + функциональный вид +
регрессионная цель.

## Виды

Функциональные:

- [Функциональное тестирование](functional-testing.md) — система делает то, что должна.
- [Приёмочное тестирование](acceptance-testing.md) — заказчик подтверждает пригодность.

Нефункциональные — [обзор](non-functional-overview.md):

- [UI-тестирование](ui-testing.md) — соответствие интерфейса макетам и стандартам.
- [UX и юзабилити](ux-usability-testing.md) — пользователь достигает цели.
- [Совместимость](compatibility-testing.md) — браузеры, устройства, разрешения, ОС.
- [Производительность](../10-performance/index.md), [безопасность и
  доступность](../11-security-accessibility/index.md).

## Как выбирать под заказ

Виды выбираются от свойств объекта, а не по списку «что бывает»:

| Свойство объекта | Обязательные виды |
|---|---|
| Есть формы ввода | функциональное, UI, валидация |
| Есть оплата | функциональное, безопасность, совместимость |
| Основной трафик мобильный | адаптивность, совместимость, производительность |
| Публичный сайт госуслуг или медицины | доступность (WCAG) |
| Есть личный кабинет | функциональное, разграничение прав, безопасность |
| Каталог с фильтрами | функциональное, производительность выборки |

Обоснование выбора записывается в [тест-план](../04-documentation/test-plan.md): вид без причины —
это либо лишние часы, либо непокрытый риск.
